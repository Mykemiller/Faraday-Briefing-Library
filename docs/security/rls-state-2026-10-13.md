## 3. Reconciliation against FDY-164 and FDY-166

**FDY-164** (status Done): *rls_disabled_in_public, 21 tables*.

1. **Partially resolved.** FDY-164 is marked Done, but the advisor still shows **1** ERROR (`spatial_ref_sys`). The fix
   comment (2026-10-12 19:05 CT) says this: 20 tables fixed, 1 accepted exception. The issue title and "Done" state still read as if all
   21 were fixed.
2. **The FDY-167 six-table list does not match FDY-164.** Only `spatial_ref_sys` appears in both lists. The other five
   FDY-167 tables are not in FDY-164's list, and RLS is already enabled on them. So FDY-167's premise that they "may be RLS-disabled" is
   false today.
3. **Grants are still in place.** The FDY-164 comment says `anon` had INSERT/UPDATE/DELETE on these tables. That is still true at the grant level:
   on all 21 tables `anon` holds SELECT and INSERT (UPDATE/DELETE were not re-measured). Deny-all RLS is the only control for 20 of them. It is no control at all for `spatial_ref_sys`.
4. Consistent: `rls_enabled_no_policy` = 510, matching the post-fix figure in the FDY-164 comment.

**FDY-166** (status Backlog): *31 anon / 134 authenticated-executable SECURITY DEFINER functions*.

5. **Counts match exactly.**

   | Count | FDY-166 | Advisor | Catalog |
   |---|---|---|---|
   | Anon-executable | 31 | 31 | 31 |
   | Authenticated-executable | 134 | 134 | 134 |
   | Authenticated only | 103 | — | 103 |

   The function names in FDY-166's highest-risk and read lists also match §1.3.
6. **Detail FDY-166 does not state:** 6 of the 31 anon grants are explicit grants to `anon`, not inherited from `PUBLIC`. These are the Workbench and
   JW map RPCs listed in §1.3. Revoking from `PUBLIC` does not remove them.
7. **FDY-166 Fix step 4 is incomplete.** The proposed fix is `alter default privileges … revoke execute on functions from public`. But
   `pg_default_acl` for schema `public` grants EXECUTE on new functions **explicitly** to
   `anon` and `authenticated`, for both `postgres` and `supabase_admin`:
   - `{postgres=X,anon=X,authenticated=X,service_role=X}`

   Revoking from `PUBLIC` alone will not stop new functions from being anon-executable. The default-privilege revoke must also name
   `anon` and `authenticated`.
8. **Confirmed:** `fn_state_overlay_refresh(text)` is SECURITY INVOKER (`prosecdef = false`), and both `anon` and `authenticated` can execute it.
   Its ACL holds both `=X/postgres` and an explicit `anon=X/postgres`. Because it is not SECURITY DEFINER, it does not appear in the advisor counts.
9. **Confirmed:** `auth.users` = 0 rows. The project's Auth sign-up setting was not checked; the SQL connector cannot read it.

**Out of scope, recorded for context:** `security_definer_view` = 0 is consistent with FDY-163 being remediated. The
remediation works through grants. 41 views still run with definer semantics (§1.2).
